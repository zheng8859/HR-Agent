## Part 2 — 哪些做得好（What went well?）

### 流程角度

1. **规格先行（OpenSpec propose → apply → archive）几乎消除返工。** 全部 31 条 `docs(openspec)` 提交严格走「提案 → 落地 → 归档」三段；文档 44 的 6 工具真实实现一次通过，联调仅暴露 1 个外键依赖删除问题（8c472c3），规格里「有依赖拒绝删除」场景已在落地前写好，修复是补实现而非改设计。
2. **原子化提交 + Conventional Commits 让历史可追溯。** 104 条提交按 `{type}({scope})` 划分，CHANGELOG 可直接由 `git log` 机械分组生成，无需人工回填；每个模型/组件独立 commit，回滚粒度到单组件。

### 技术角度

1. **pgvector 一体化存「业务 + 向量」省掉一套独立向量库。** 文档 39 把 Document 的 embedding（1536 维）直接落在 PostgreSQL 的 pgvector 列上，RAG 检索走同库 SQL，省去 ES/独立向量服务的运维与一致性同步；L3 知识问答 30/30 验证了该决策可行。
2. **SSE 统一「对话流 + 任务流」协议。** 前端仅实现一个 `createSSEDecoder`（`@/utils/sse`）就同时消费 `thinking→plan→delta→final`（对话）与 `progress→delta→artifact→final`（任务）两套事件序列，内嵌工具面板按 `artifacts[].type` 切换，复用一个消费链路，代码量远低于逐工具定制渲染。

### 协作角度

1. **TDD 下 regression 发现时间大幅缩短。** 文档 44 的删除依赖问题若在无测试情况下暴露，会以「SSE 断流（curl exit 18）」这种难以定位的形态出现；因为 `test_agent_skills.py` 有 `test_delete_jd_with_dependents_refuses`，直接定位到 `_execute_delete` 的外键检查缺口，修复 + 复验 < 10 分钟。
2. **文档驱动 + 明确「何时用什么」决策表，避免了工具选择内耗。** CLAUDE.md 里「设计已定义 → /opsx」「架构决策 → /plan-eng-review」的决策表，让 13 份文档的执行没有在中途反复讨论方案，节奏稳定推进到 v1.0.0。

## Part 3 — 哪些可以改进（What can be improved?）

### 流程角度

1. **Evals 全量（含 L3）每次跑偏慢。** `run_evals --tier all` 需要 `--run-slow` 才带 L3 的 120 条，且 L3 依赖 mock/外部服务，收工前全量一次约数分钟。**改进**：引入增量 Evals——按变更 scope（如 `jd` / `rag`）只跑受影响 tier，配合 GitHub Actions 门禁（7cbb531）在 PR 层做全量，本地收工只跑 `--tier l1`。
2. **`/no-mistakes` 检查项中有「Dockerfile/compose 就绪」但文档 34~45 未预留生产镜像，直到文档 46 才补齐。** 发布前才补生产化产物，风险后移。**改进**：在文档 34（环境搭建）即产出生产 Dockerfile 骨架，后续每个阶段 CI 里跑一次 `docker build` 冒烟，把「能构建」纳入 pre-push。

### 技术角度

1. **`SECRET_KEY` 默认占位符贯穿全程，到文档 45 安全审计才标记为 Medium。** 代码默认 `change-me-in-production`，本地/测试可跑但生产必须替换，这个约束只在 `.env.example` 注释里。**改进**：`config.py` 启动时若 `SECRET_KEY` 为占位值且 `ENV=production` 则直接拒绝启动（fail-fast），把配置错误拦在进程启动而非上线后。
2. **前端 chunk 体积偏大（DashboardView 1.1MB、index 871KB）。** ECharts 全量引入导致看板页单 chunk 超 500KB 阈值。**改进**：ECharts 按需引入（`echarts/core` + 用到的 chart/component）或对 DashboardView 做 `defineAsyncComponent` + `manualChunks` 拆分，把首屏体积降到 ~300KB。

### 产品角度

1. **知识问答覆盖率受限于向量相似度阈值，无依据时正确拒答，但「该答没答」未量化。** L3 只测拒答正确率，未测「应召回未召回」的漏召。**改进**：Golden 集增加「正例必须命中」的召回率指标（recall@k），与拒答准确率并列进 L3 红线。
2. **简历评估五维度评分依赖 Dify type=3，未配置时降级 mock，生产真实效果未验证。** 本地联调仅验证了「请求发出 + 产物返回」，未验证真实 Qwen 评分质量。**改进**：在 `.env.production` 配真实 Dify key 后跑一轮 L2 dify 40/40，作为上线前最后一道验证。
