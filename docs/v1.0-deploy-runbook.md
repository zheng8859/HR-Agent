# v1.0.0 灰度发布运维手册（doc 46 Step 2/3）

> 对应文档 46 的 `/land-and-deploy`（Step 2）与 `/canary`（Step 3）。
> Gstack 命令在本环境不可用，本文档以**等价手工 runbook** 形式固化四级灰度扩量、监控指标、回滚决策。
> 注：本环境为本地开发机、无生产服务器（无 SSH 目标），**线上灰度扩量已按「文档化 + 待执行」处置**；下述步骤在拿到生产服务器后照此执行即可。

---

## 一、部署前置

1. 服务器：SSH 可达、Docker ≥ 24、磁盘剩余 > 10GB。
2. 拉取代码：`git fetch origin && git checkout v1.0.0`。
3. 配置：`cp .env.production.example .env.production` 并填入真实值（**必须**替换 `SECRET_KEY` 与 `POSTGRES_PASSWORD`，`openssl rand -hex 32` 生成密钥）。
4. 首次建表（幂等）：
   ```bash
   docker compose -f docker-compose.prod.yml --env-file .env.production run --rm backend alembic upgrade head
   ```
5. 启动全量栈：
   ```bash
   docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build
   ```

## 二、四级灰度扩量（5% → 25% → 50% → 100%）

> 灰度通过 Nginx 按用户/会话分流：以 `X-Canary` header 或权重 upstream 切流量，新版本后端起独立副本。

| 阶段 | 流量 | 观测时长 | 通过条件 |
|------|:---:|:---:|------|
| 金丝雀 5% | 5% | ≥ 2h | 错误率 < 1%、p95 < 500ms、Agent 成功率 > 95% |
| 25% | 25% | ≥ 1h | 错误率 < 1%、重点看 DB 连接池 |
| 50% | 50% | ≥ 1h | 错误率 < 1%、DB 连接池 < 80% |
| 100% | 100% | — | 稳定无告警，全量发布 |

## 三、监控指标与告警阈值

| 指标 | 正常值 | 告警阈值 | 说明 |
|------|:------:|:------:|------|
| API 错误率 | < 0.5% | > 5% P0，> 1% P1 | 5xx 占全部请求比 |
| API p95 延迟（非 LLM） | < 300ms | > 3s P1 | 不含 Agent 对话等 LLM 调用 |
| Agent 对话成功率 | > 95% | < 90% P1 | 返回有意义回复（含工具调用成功）比例 |
| 简历评估成功率 | > 95% | < 90% P1 | Dify type=3 返回有效评分 |
| 知识问答拒答正确率 | > 90% | < 80% P1 | 无依据时正确「资料不足」比例 |
| 数据库连接池使用率 | < 60% | > 90% P1 | 接近上限需扩容 |

## 四、回滚预案

- **稳定版本**：`git tag v0.6.0`（commit `f663d2f`）为上一稳定发布，可直接回切。
- **回滚步骤**（任一阶段出现 P0 告警立即执行）：
  ```bash
  docker compose -f docker-compose.prod.yml --env-file .env.production down
  git checkout v0.6.0
  docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build
  ```
- 数据卷 `hragent_pgdata` 保留，`down` 不清除数据；仅 `down -v` 才销毁（回滚不执行 `-v`）。

## 五、决策树

- 任一阶段 P0（错误率 > 5%）→ 立即终止扩量，回滚上一阶段，定位后重启灰度。
- P1（错误率 > 1% / 延迟 > 3s / DB 池 > 90%）→ 冻结当前阶段，观察 30min，未恢复则回滚。
- 全绿 → 推进下一阶段。
